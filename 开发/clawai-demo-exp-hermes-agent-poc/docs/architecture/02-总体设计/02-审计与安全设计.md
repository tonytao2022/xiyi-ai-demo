# 审计与安全约束

## Trace 设计

- 每个分析任务必须由 `BFF` 生成全局唯一的 `traceId`。
- `traceId` 必须贯穿 `BFF`、`OpenClaw`、`语义层`、`规则引擎`、`报告服务`。
- 任一服务内部产生的子步骤可扩展 `spanId`，但不得替代 `traceId`。
- 报告落库时必须把 `traceId` 写入 `reportMeta` 与 `auditTrail`。

## 审计日志要求

所有受控工具调用都应记录以下最小字段：

- `traceId`
- `actorId`
- `tenantId`
- `skillKey`
- `toolKey`
- `startedAt`
- `finishedAt`
- `durationMs`
- `requestSummary`
- `responseSummary`
- `resultStatus`
- `failureReason`

## 工具白名单

- 工具白名单按分析技能分组，例如 `business_diagnosis`、`capacity_analysis`、`inventory_health`。
- `OpenClaw` 仅能调用当前技能显式授权的工具集合。
- 白名单工具必须声明输入输出协议、调用方、审计等级与超时策略。
- 不提供面向模型的“工具发现市场”或任意 HTTP 代理能力。

## 数据库访问约束

- 模型与 OpenClaw 插件均不得直连数据库。
- 所有数据访问必须通过 `语义层` 暴露的指标 API 或模板查询接口。
- 语义层必须拒绝原始 SQL 字符串输入，只接受受控查询对象。
- 查询结果必须返回指标口径版本、数据时间戳、来源系统与查询审计 ID。

## 结果可信性约束

- 核心数字必须能够回溯到 `metricKey`、过滤条件、时间范围、数据时间戳。
- 核心结论必须标明来源：`rule`、`model` 或 `hybrid`。
- `rule` 结论必须关联规则版本；`model` 结论必须关联所依赖的事实与提示模板版本。
- 报告服务不得改写规则引擎输出的定量结论，只能整合与格式化。

## 高信任代码治理

- `plugins/openclaw-domain-tools` 与 `services/openclaw-runtime` 视为高信任后端代码。
- 高信任代码必须做独立代码审查，并限制配置项与密钥暴露面。
- 插件只保留必要环境变量，不向模型泄露连接串、令牌或私有端点。
- 生产环境应为不同租户保留清晰的访问边界与审计边界。
