# 1. 首个 Demo 业务确认清单

## 1.1 目标

整理“在线一次校验合格率管控”场景在正式开发前仍需由业务同事确认的关键问题，作为数据、规则、展示和验收标准的统一确认清单。

## 1.2 使用方式

- 本文档建议由产品、业务、数据和研发共同对齐。
- 每个问题建议补充一列“确认结果 / 备注 / 负责人 / 确认时间”。
- 已确认事项可同步回写到 `docs/data/` 和 `docs/architecture/` 对应文档。

## 1.3 已确认事项

### 1.3.1 一次校验合格率口径

- 一次校验合格率按**批次数**统计，不按重量统计。
- `mat_no` 作为批次唯一关联键。
- 主判定字段当前默认采用 `pch_judge_code`。
- 判定值处理规则：
  - `S`：合格
  - `A/B/F`：不合格
  - `N`：从分母中排除
- 主统计过滤条件当前默认采用 `stock_oper_order = "ZKI"`。

### 1.3.2 待保留为默认判断

- 主统计表当前默认采用 `tsh_pro_stock_record`
- 主统计时间字段当前默认采用 `stock_chng_time`

以上两项目前仍建议业务再做一次确认。

## 1.4 需业务确认的问题

## 1.4.0 重点问题总览

以下问题建议优先确认，确认后即可明显降低后续语义层、规则引擎和前端展示的返工风险：

- 【重点】`pch_judge_code` 是否就是最终判定字段，还是需要叠加 `complex_judge_code`
- 【重点】`tsh_pro_stock_record` 是否就是一次校验合格率统计主表
- 【重点】一次校验合格率按日/周统计时，是否统一按 `stock_chng_time`
- 【重点】`stock_oper_order = "ZKI"` 是否为唯一有效统计范围
- 【重点】`tsh_pro_stock_record`、`tdmmm`、`tqmtq_entrust_result` 的主关联关系是否准确
- 【重点】检验项目如何归类为“磁物类 / ICP类 / 粒度类 / 其他类”
- 【重点】首版 demo 最少必须展示哪几个结果，业务才会认可
- 【重点】哪些结论必须由规则引擎输出，不能交给模型自由生成

### 1.4.1 场景边界

1. 首版 demo 是否只覆盖单工厂、单车间/单产线？
   - 建议答案：是。首版先收敛到单工厂、单车间/单产线，避免一开始引入多工厂横向对比和跨组织权限问题。
2. 当前统计对象是否只看成品批次，不包含半成品或中间品？
   - 建议答案：是。首版只看成品批次，半成品和中间品先不纳入主指标统计范围。
3. 时间粒度是否首版只支持日和周？
   - 建议答案：是。首版先支持日和周，月度和季度可后置。
4. 当前 demo 是否先不做多工厂对比、历史版本对比和自由问答？
   - 建议答案：是。首版先聚焦单场景、单链路、结构化报告，不做自由问答和复杂对比分析。

### 1.4.2 主指标口径

1. 【重点】`pch_judge_code` 是否就是最终判定字段，还是需要叠加 `complex_judge_code`？
   - 建议答案：首版先以 `pch_judge_code` 为主判定字段；`complex_judge_code` 保留为待二次确认项，暂不进入主公式。
2. `N` 从分母中排除是否符合最终业务口径？
   - 建议答案：符合。`N` 代表未判定，不应进入已判定批次总数。
3. 是否还有其他判定值也应被排除或单独处理？
   - 建议答案：当前默认没有，先只处理 `S/A/B/F/N` 五类值；若后续发现其他状态值，再补充规则。
4. 一次校验合格率是否需要同时展示“合格率”和“不合格率”两种表达？
   - 建议答案：需要。首版建议主展示“合格率”，辅助展示“不合格批次数”或“不合格率”，便于业务直观理解异常规模。

### 1.4.3 主表与关联关系

1. 【重点】`tsh_pro_stock_record` 是否就是一次校验合格率统计主表？
   - 建议答案：是。首版先将其作为主统计表，因为统计范围过滤条件和时间字段都落在这张表上。
2. `tsh_pro_stock_record` 与 `tdmmm` 是否通过 `mat_no` 关联？
   - 建议答案：是。当前默认 `mat_no` 为批次唯一关联键，两表先通过该字段关联。
3. 【重点】`tdmmm` 与 `tqmtq_entrust_result` 是否通过 `entr_no` 关联？
   - 建议答案：是。当前默认通过 `entr_no` 关联，用于把批次判定结果追溯到具体检验项目结果。
4. 工序投入表与工序产出表最可靠的关联键是什么？
   - 建议答案：当前默认优先使用 `seq_no` + 批次链路联合判断，后续需结合真实表结构确认是否存在更稳定的主外键。
5. 是否存在一对多、多对多或中间表关联场景需要特别说明？
   - 建议答案：大概率存在，尤其在委托结果和工序追溯链路上；首版应默认按一对多处理，并在文档中标记为重点确认项。

### 1.4.4 时间与过滤条件

1. 【重点】一次校验合格率按日/周统计时，是否统一按 `stock_chng_time`？
   - 建议答案：是。首版先统一按 `stock_chng_time` 所属自然日/周统计，便于口径收敛。
2. 【重点】`stock_oper_order = "ZKI"` 是否为唯一有效统计范围？
   - 建议答案：是。首版先写死 `ZKI` 作为唯一统计入口，若后续业务要求纳入其他指示值，再扩展。
3. 是否还有其他过滤条件必须加上，例如工厂、库别、状态位、封锁标记？
   - 建议答案：建议加。首版至少保留工厂/车间过滤，同时建议评估是否排除 `hold_flag` 为封锁的批次。
4. 是否需要排除返工批次、测试批次、作废批次或封锁批次？
   - 建议答案：需要。首版建议默认排除测试批次、作废批次和明确封锁批次；返工批次是否排除建议由业务再明确。

### 1.4.5 不合格项目结构

1. `tqmtq_entrust_result` 中哪些字段可以用于判定“具体是哪项不合格”？
   - 建议答案：首版默认使用 `item_code`、`item_name`、`act_result_value`，由 `item_code/item_name` 标识项目，`act_result_value` 作为结果值参考。
2. 【重点】检验项目如何归类为“磁物类 / ICP类 / 粒度类 / 其他类”？
   - 建议答案：首版建议由业务提供一份“项目编码/项目名称 -> 项目类别”的映射表，先不要让系统自动推断。
   - 补充：`dict_type = qm_test_type` 的字典表结构、`item_code` 与字典对齐方式、以及**仅用于模拟 Demo 的关键词降级归类**见 `06-首个demo-检验项目字典与分类映射.md`；上线口径以业务映射表为准。
3. 项目结构分析是按项目明细展示，还是按项目类别汇总展示？
   - 建议答案：两者都需要。首版页面主展示按项目类别汇总，必要时在表格中下钻到项目明细。
4. 若同一批次存在多个不合格项目，统计时如何去重或累计？
   - 建议答案：首版建议按“项目累计”统计结构分布，不按批次去重；但批次层面的不合格批次数仍只按批次记一次。

### 1.4.6 混料与原料追溯

1. 混料重量是否只作为解释线索，不进入主指标公式？
   - 建议答案：是。首版默认混料重量只作为解释线索，不直接进入一次校验合格率主公式。
2. 哪些场景下需要把混料作为重点异常原因？
   - 建议答案：当异常批次集中出现在有混料记录的批次上，且主导不合格类别与原料性质相关时，把混料作为重点原因候选。
3. 工序投入产出追溯时，业务最认可的追溯链路是哪条？
   - 建议答案：首版默认按“工序产出表 -> `seq_no` / 批次链路 -> 工序投入表 -> 原料批次”追溯。
4. demo 首版是否必须展示原料批次关联结果？
   - 建议答案：建议展示。至少以“原料批次关联线索卡片或表格”的形式出现，增强 demo 价值感。

### 1.4.7 设备事件关联

1. 设备故障、维修、保养事件是否都要纳入时间线？
   - 建议答案：是。首版建议都纳入，但在展示上区分事件类型。
2. 哪类设备事件才算“对质量波动有参考意义”？
   - 建议答案：优先纳入故障发生、维修完成、保养完成这三类关键节点，普通状态变更可后置。
3. 设备事件是作为辅助线索，还是可能成为主要原因结论？
   - 建议答案：首版先作为辅助线索，不直接成为主因结论；除非业务明确给出规则判定条件。
4. 首版 demo 是否必须展示设备事件对照图或事件列表？
   - 建议答案：建议展示，但可以先做事件列表或时间线卡片，不一定一开始就做复杂图表。

### 1.4.8 首版展示与验收

1. 【重点】首版 demo 最少必须展示哪几个结果，业务才会认可？
   - 建议答案：至少展示 4 个结果：
     - 一次校验合格率趋势
     - 不合格批次数
     - 不合格项目结构分布
     - 结论与建议
2. 当前建议优先展示：
  - 一次校验合格率趋势
  - 不合格批次数
  - 不合格项目结构分布
  - 结论与建议
  - 原料批次/混料关联线索
  - 设备事件时间线
   请确认哪些是必须、哪些可以后置。
   - 建议答案：
     - 必须：一次校验合格率趋势、不合格批次数、不合格项目结构分布、结论与建议
     - 推荐首版一并展示：原料批次/混料关联线索
     - 可后置：设备事件时间线（若时间紧，可先做简化列表）
3. 哪 3 个数字必须保证准确且可追溯？
   - 建议答案：
     - 一次校验合格率
     - 不合格批次数
     - 各类不合格项目占比
4. 【重点】哪些结论必须由规则引擎输出，不能交给模型自由生成？
   - 建议答案：
     - 是否异常
     - 哪些批次被判定为不合格
     - 哪类不合格项目占比最高
     - 是否存在明确的原料/设备关联线索
     - 建议动作中的规则性结论
