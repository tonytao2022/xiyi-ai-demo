## 一、核心结论

### 1.1 四层架构MySQL落地 (Antony的议题)

**数据库命名**：使用独立数据库 `xiyi_quality`，共27张核心表

| 层级 | 表数量 | 核心表清单 |
|------|--------|-----------|
| **数据采集层** | 4 | `ds_data_source`, `ds_table_metadata`, `ds_column_metadata`, `ds_mapping_rule` |
| **数据治理层** | 10 | `dg_standard_dict`, `dg_standard_dict_item`, `dg_standard_column`, `dg_indicator_atom`, `dg_indicator_derived`, `dg_indicator_category`, `dg_indicator_category_mapping`, `dg_quality_rule`, `dg_quality_check_log`, `dg_quality_report`(预留) |
| **数据应用层** | 13 | `ap_scene_config`, `ap_scene_step`, `ap_scene_ds_binding`, `ap_analysis_model`, `ap_model_input_param`, `ap_analysis_instance`, `ap_analysis_step_log`, `ap_capa_plan`, `ap_capa_task`, `ap_capa_task_track`, `ap_scene_report_tpl` |
| **数据展现层** | 0 | 展现层无独立表，所有数据来自应用层API |

**核心设计原则**：
- `ap_scene_config` + `ap_scene_step` 实现场景配置完全驱动
- 新增场景只需要INSERT配置，无需改代码
- 每个场景的步骤、数据源、分析模型、报告模板全部通过关联表配置

**场景配置表结构**：
```
ap_scene_config (场景主表)
  ├── scene_code: UNIQUE编码 (QUAL_01~QUAL_07)
  ├── scene_name/desc/role_type/icon/sort_order
  ├── 1:N → ap_scene_step (步骤定义)
  │     ├── step_code, step_name, step_type, sort_order
  │     ├── 绑定 → ap_analysis_model (分析模型)
  │     └── 绑定 → ap_scene_report_tpl (报告模板)
  ├── 1:N → ap_scene_ds_binding (数据源绑定)
  │     └── 引用 → dg_indicator_atom / dg_standard_column
  │                   └── 引用 → ds_table_metadata / ds_column_metadata
  └── 1:N → ap_analysis_instance (运行实例)
```

### 1.2 数据源抽象元数据方案 (Hugo的议题)

**三层映射架构**（源 → 标准 → 应用）：

```
[实际数据源]  →  ds_column_metadata  →  dg_standard_column  →  ap_scene_ds_binding
(ERP/MES字段)  (采集层原始注册)        (治理层标准化)            (应用层绑定)
```

**关键设计**：
- `ds_mapping_rule` 实现源字段→标准字段的转换规则（支持direct/transform/constant/lookup四种类型）
- `dg_indicator_atom` 定义原子指标的计算口径、维度标签、红黄绿阈值
- `dg_indicator_derived` 支持公式表达式引用原子指标的组合计算
- `dg_standard_dict` 管理所有枚举值和编码标准（如缺陷代码、检验类型、单位体系）

### 1.3 管理配置界面设计 (Tony的议题)

**6大配置菜单**：
1. 场景配置（列表→步骤编排→数据绑定→报告模板）
2. 数据源管理（注册→表导入→字段映射→同步策略）
3. 指标管理（分类树→原子→派生→看板预览）
4. 数据标准（字典→标准字段→格式规范）
5. 质量规则（定义→调度→日志→报告）
6. 分析模型（注册→参数→版本→测试）

**前端风格统一方案**：
- 复用stock-manager深色工业风CSS变量体系(`--bg-primary: #0a0e17`, `--bg-card: #161d2a`等)
- 新增品质场景特有色彩变量（质量绿`#10b981`、缺陷红`#ef4444`、追溯紫`#8b5cf6`等）
- 独立SPA页面`quality-workbench.html` + 单独8890端口，物理隔离不干扰股票系统
- 配置管理页面与品质工作台共用同一SPA框架

## 二、对3位角色的具体回应

### ✅ Antony — 你的3个问题

**Q1: 四层架构如何落地MySQL？**
> 详见上面的27张表设计。核心是"配置驱动"：所有业务逻辑通过配置表定义，运行时通过`ap_scene_step`→`ap_analysis_model`→`ap_model_input_param`链路驱动，无需硬编码。

**Q2: 场景配置表结构？**
> 一个场景需要配置：①基本信息(scene_config)、②多步骤定义(scene_step, 含顺序/模型绑定/模板绑定)、③数据源绑定(scene_ds_binding, 链式引用到治理层和采集层)、④报告模板(step→report_tpl)。**新增场景=INSERT几条配置记录**。

**Q3: 七步分析流程如何结构化存储？**
> 通过`ap_scene_step`表的`step_type`枚举(definition/analysis/correlation/verification/attribution/solution/tracking)和`sort_order`定义流程。运行时`ap_analysis_step_log`记录每步的执行输入/输出/AI推理过程。支持跳过步骤、人工干预、回退重做。

### ✅ Hugo — 你的3个问题

**Q1: 7场景数据源如何抽象成通用元数据？**
> 采用"三层映射"架构：采集层`ds_column_metadata`注册原始字段→治理层`dg_standard_column`标准化→应用层`ap_scene_ds_binding`绑定。同时通过`dg_standard_dict`统一管理所有枚举值（缺陷代码、检验类型等）。

**Q2: 数据治理层基础表？**
> 6张：`dg_standard_dict`(字典)、`dg_standard_dict_item`(条目)、`dg_standard_column`(标准字段)、`dg_indicator_atom`(原子指标)、`dg_indicator_derived`(派生指标)、`dg_quality_rule`(质量规则)。配套执行日志表`dg_quality_check_log`。

**Q3: 各场景字段如何映射？**
> 通过`ds_mapping_rule`表定义源字段→标准字段的映射规则。例如MES的`qc_result`字段映射到标准字段`QUAL_INSPECT_RESULT`，再映射到指标`QUAL_PASS_RATE`。每个场景通过`ap_scene_ds_binding`关联到对应的标准字段/指标。

### ✅ Tony — 你的3个问题

**Q1: 配置界面设计？**
> 6大配置菜单，覆盖场景、数据源、指标、标准、质量规则、分析模型的全生命周期管理。最复杂的页面是"拖拽式步骤编排器"和"源→标准字段映射器"。

**Q2: 数据治理层前端页面？**
> 需要：指标看板(分类树+预览)、字典管理(CRUD+树结构)、标准字段管理(列表+关联)、质量规则编辑(SQL编辑器+调度配置)、稽核日志查看(列表+详情)。

**Q3: 与stock-manager风格统一？**
> 采用"同一深色工业风CSS体系 + 独立SPA端口"方案。直接复用stock-manager的:root变量定义(背景/卡片/文本/边界)，新增品质行业特定色彩。不做代码级别合并，避免相互影响。
